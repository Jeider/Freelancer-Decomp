# Режим сборки для выпуска

Обычный `Release` остаётся рабочей сборкой с диагностикой. Для выпуска:

```powershell
python tools/train_courier/build.py Common Server Content freelancer --production
```

Результат: `src/obj/production/rpg1/bin/`. Скрипт ничего не устанавливает в игру.
Сохраняются RP9 и RPG-функции, выбранные обычным скриптом сборки. Это сборка
перечисленных проектов, а не упаковщик полного дистрибутива игры.
После первой сборки Common для обновления одного клиента:
`python tools/train_courier/build.py freelancer --production`.
При изменении интерфейсов Common пересобирайте его вместе с клиентом:
`python tools/train_courier/build.py Common freelancer --production`.

MSBuild-переключатель: `/p:FreelancerProduction=1` (по умолчанию 0).
При прямом вызове MSBuild используйте отдельные OutDir/IntDir для production.

В этом режиме на этапе компиляции отключены:

- watchdog зависаний (опрос кадров, приостановка потока и дампы зависаний);
- старый клиентский обработчик с запуском dxdiag/dw15;
- tick profiling.

Дампы при крашах и расшифровка стека через dbghelp сохранены. При необработанном
исключении клиент пишет `.dmp` и `.txt` в `<game>/CRASHDUMPS`, затем завершает
процесс; если дамп отключён или запись не удалась, управление получает Windows.
`port.ini [Debug] crash_dumps` (по умолчанию 1) и `crash_dumps_keep` (100)
продолжают действовать. Для разбора сохраняйте PDB именно от выпущенной сборки.
`hang_dump_seconds` не включает watchdog в production.
`port.ini` не может включить исключённую диагностику. Обычные журналы ошибок,
игровые функции и ABI-настройка `_ITERATOR_DEBUG_LEVEL=1` сохраняются.
PDB сохраняются для разработчика; режим не отключает вообще все логи и
диагностику во всех DLL. Проверка запуска игры перед выпуском всё ещё нужна.

Первоначально 13 ноября 2026 были собраны Common + freelancer с `--production`
и freelancer в обычном режиме. Затем по просьбе пользователя в production
возвращены дампы крашей; watchdog и старый crash reporter остаются выключены.
Обновлённый production-клиент собран: MiniDumpWriteDump присутствует, а
dxdiag.exe, dw15.exe, SuspendThread, GetThreadContext и hang_dump_seconds
отсутствуют в EXE. Создание дампа намеренным крашем не проверялось.
Рабочая игра не обновлялась, запуск production-сборки и проверка на другом ПК
не выполнялись.

## Сообщение Defender, 13 ноября 2026

Пользователь сообщил: на другом ПК `freelancer.exe` определён как
`Trojan:Win32/Bearfoos.A!ml` после первого запуска. Точное время относительно
появления меню/зависания, журнал Defender и SHA256 удалённого файла пока неизвестны.

Локальный исследованный файл `D:/Games/FL_MOD/bin/freelancer.exe`:

- SHA256: `9A7EFAADED6D17E0DED224A8152B7A6E32C1C74814773DF5CC24BE8F28DAC9E5`;
- 3309056 байт, без Authenticode-подписи;
- совпал с `src/obj/train_courier/rpg1/bin/freelancer.exe`;
- обычная структура PE/MSVC, без overlay и секций с одновременными W+X;
- статический отчёт: `tools/exe_audit/report.json`.

В исходниках обнаружены собственная диагностика дампов и старый crash reporter.
Watchdog стартует при инициализации, но SuspendThread/GetThreadContext и дамп
вызываются только после зависания (по умолчанию 30 секунд), после первого кадра,
при активном окне игры. Запуск сам по себе не означает, что эти операции выполнялись.

Причина обнаружения не установлена; ложное срабатывание не подтверждено.
Production-режим добавлен для сокращения диагностики выпуска, а не как
подтверждённое исправление обнаружения Defender. Для продолжения расследования
нужны журнал защиты и хеш файла с другого ПК. Файл внешним сервисам не отправлялся.
