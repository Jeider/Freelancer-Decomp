# Разметка базовых участков m01a

## Обновление: персональный старт на Сигме-13

В Content реализован адаптер только для `Mission_01a` сюжетного сервера.
Он обрабатывает `real_mission_init`, `init_bar`, `START_vendor_do_accept` и
`return_to_deck` персонально, даже если в сгенерированном INI нет execution_scope.
Исходники Pythonlancer и DATA для этого не меняются: регенерация не стирает адаптер.
SP использует прежние триггеры без адаптера.

Каждый участник получает собственную посадочную RTC, Аларика, ответ на предложение,
корабль и палубную сцену. MissionResponse проверяется по controller/player; ответ
одного персонажа не проходит в банк другого. Цели фильтруются по игроку, заголовок
и описание сохраняются в банке, сообщения не рассылаются группе. Общие эффекты
принятия задания выполняются один раз, без JoinMissionAsGroup из личного ответа.
Три разрешённых перехода в общий scope — LAUNCH_SIG13, LAUNCH_SIG13_COMPLETE и
MSN_REP_BEFORE — ставятся в очередь после выхода из личного контекста и активируются
однократно. Общее космическое прохождение по-прежнему привязано к ведущему.

Присоединение происходит также на BaseEnter, до первой комнаты. При создании
личного банка воспроизводится его текущая база, чтобы не терять начальную сцену.
RTC уже используют серверный фильтр PlayerId; сцены разных участников раздельны.
Проверки используют фактические четыре блока из рабочей DATA/m01a.ini и штатный
парсер/планировщик с имитацией игроков и побочных эффектов. Проверены два участника,
поздний вход, чужой controller, дубли ответа, один общий спавн и восстановление
личного прогресса при смене сетевого слота. Проверка двумя игровыми клиентами
ещё нужна. Полное сохранение общей кампании/смена ведущего остаются отдельной задачей.

Шаринг Берлинской сцены, остального интро, командный взлёт и отображение гуляющих
игроков в этот этап не входят. Ниже сохранён предыдущий разбор всей m01a;
его патч-предложение на семь триггеров по-прежнему не устанавливается целиком.

Статус: предложение подготовлено, в исходный шаблон и DATA не установлено.
Автоматически ставить его в игру сейчас нельзя: часть триггеров будет отвергнута
текущим LocalTriggers, а связи между локальными и глобальными цепочками оборвутся.

Исследованы только `templates/missions/m01/m01a.ini` и включаемый исключительно
им `templates/missions/m01/_intro.ini`. Файлы m01b и остальных миссий не менялись.
Ссылка на RTC `missions/m01b/berlin.ini` находится в m01a; сам RTC не изменяется.

| Триггер | Назначение | Предлагаемый scope |
|---|---|---|
| BARMAN_init | Разговор с барменом на the_intro_base | local |
| INTRO_CITYSCAPE | Сцена в городе the_intro_base | local |
| real_mission_init | Посадочная сцена на sig13_01_base и цель поиска работы | local |
| init_bar | Встреча с Алариком в баре | local |
| START_vendor_do_accept | Личное принятие задания, запись в журнал, выдача корабля | local |
| return_to_deck | Получение корабля на палубе | local |
| Player_on_berlin_planet | Сцена после посадки на rh_ber_01_base | local после отделения NagOff |
| berlin_rtc_complete | Завершение общей миссии через Act_ChangeState | global |
| INTRO_forceland, remove_playership | Переход из космического интро на базу | global до переработки общего интро |
| LAUNCH_SIG13, LAUNCH_SIG13_COMPLETE | Запуск космической части и появление Аларика | global |

`berlin_rtc_complete` нельзя объявлять локальным целиком: Act_ChangeState = SUCCEED
завершает общий контроллер. Личное завершение сцены и общее завершение миссии
необходимо разделить. Сейчас условие здесь — вход в Cityscape, не RTCDone.

## Препятствия для включения

1. `START_vendor_do_accept` использует `system`, `Cnd_MsnResponse`,
   `Act_NNIds` (history), `Act_SetNNObj`, `Act_SetTitle` и `Act_SetOffer` (offer.init).
   Эти ключи не входят в whitelist LocalTriggers. Нужна поддержка адресованного
   ответа MissionResponse (поле player в words[3], controller в words[0]).
   Вызывать штатный OnOfferResponse для каждого гостя нельзя: он уведомляет общий
   Story и выполняет JoinMissionAsGroup.
2. `real_mission_init` содержит неподдерживаемый `Act_SetNNObj`;
   `Player_on_berlin_planet` — `Act_NagOff`. Последний управляет общим nag,
   его следует вынести в глобальную цепочку.
3. Act_SetNNObj меняет цели всех записей Mission->Players и сбрасывает общий NnPath.
   Act_NNIds и Act_SetOffer отправляют DisplayMissionMessage с broadcast=true.
   Простое расширение whitelist нарушит персональность. Нужна изоляция целей,
   заголовка/описания и отправка истории только адресату.
4. Глобальные триггеры сейчас не могут активировать local, а local — global.
   Входы: STORYLINE_START -> BARMAN_init; INTRO_forceland -> real_mission_init;
   near_berlin_planet -> Player_on_berlin_planet.
   Выходы: INTRO_CITYSCAPE -> INTRO_spaceflight; START_vendor_do_accept ->
   LAUNCH_SIG13, LAUNCH_SIG13_COMPLETE, MSN_REP_BEFORE;
   Player_on_berlin_planet -> berlin_rtc_complete.
   Нужны явные правила перехода: активация для участников и поздно вошедших,
   защита общего спавна от повторных личных ответов. Простой fallback в общий map
   может повторно активировать уже завершившийся глобальный триггер.
5. Автозапуск CampaignStory происходит уже после входа в комнату. Первое событие
   BaseEnter к этому времени прошло. Нужна инициализация личной цепочки текущим
   местоположением либо отдельный начальный триггер. Один InitState = ACTIVE
   не решает отсутствующих переходов между scope.

Артефакт: `out/m01a_scopes/m01a.patch`, кандидат шаблонов —
`out/m01a_scopes/proposal/missions`. Генератор предложения:
`tools/train_courier/prepare_m01a_scopes.py`.
Он не пишет за пределами рабочей копии и не запускает генерацию сцен.
# Исправление персонального предложения Аларика

Автоприсоединение через `SetMsnID` заранее заполняет на клиенте состояние принятой
групповой миссии. Обычный RTC offer type 3 после этого не отправлял `MissionResponse`:
персональный `START_vendor_do_accept` не получал событие и не выдавал корабль.

Локальные RTC с предложением теперь получают `PersonalStoryOfferType` в существующем
поле ScriptBehavior. Клиент показывает обычное окно предложения, но отправляет ответ
и выбирает ветку accept/reject независимо от состояния групповой миссии. Глобальные
RTC и одиночная игра сохраняют прежний тип. Требуются обновлённые Content.dll на
сервере и freelancer.exe у каждого участника; компиляция DATA не нужна.

Проверки: `tools/train_courier/check_personal_offer_bundle.py` воспроизводит старый
сбой на настоящих клиентских методах и проверяет ответы ведущего/гостя, отказ,
защиту от повторного ответа, обычный MP/SP и персональную цепочку m01a.
Это автоматические проверки с заглушками окружения; выдачу в живой сетевой игре
после исправления ещё необходимо подтвердить.
