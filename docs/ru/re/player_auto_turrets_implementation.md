# План реализации автотурелей игрока

[English](../../re/player_auto_turrets_implementation.md) · **Русский**

Исторический план от 2026-10-27. Реализация начата: контроллер SP, HUD и клавиатурные команды добавлены в исходники. Перед использованием см. [реализованное поведение, настройки и проверки](../player_auto_turrets.md): предложенные ниже имена API, параметры и будущие критерии готовности реализованы не все. Исходный план сохранён как исследование и перечень дальнейшей работы.

## Результат первого заказа

Игрок пилотирует корабль и стреляет основными пушками; назначенные турели по явному приказу сопровождают указанного противника либо самостоятельно выбирают обнаруженных врагов. Управление доступно под группами орудий. Автопилот, камера турели, навыки и новые слоты оборудования не нужны.

Предлагаемая первая версия: **SP, энергетические турели с неуправляемыми снарядами против кораблей**. Исключить ракеты, торпеды, мины, контрмеры, боеприпасные орудия и специальный путь `force_gun_ori`. Это граница первого этапа, а не ограничение архитектуры. MP и боеприпасные турели выпускать отдельно после соответствующих проверок. Ни одно предложение ниже не является уже существующим ключом INI или API.

Обычные NPC продолжают использовать существующий AI. Клиентский контроллер игрока не включает его `ScanAutoTurretTargets/FireAutoTurrets`, не отдаёт команды корабельному автопилоту и не меняет общий архетип оружия.

## Решения по управлению

| Действие | Результат |
|---|---|
| Запуск игры, загрузка, новый корабль | Ручное управление; разрешение автоматического огня не восстанавливается |
| Выбрать режим в настройке | Меняется предпочтение; стрельба не начинается |
| Нажать Auto Turret при выключенной автоматике | Выдать приказ выбранного режима; для режима цели зафиксировать текущий обнаруженный враждебный корабль |
| Нажать Auto Turret при действующем или приостановленном приказе | Немедленно отменить приказ и вернуть турели ручному управлению |
| Режим «Указанная цель» | Сопровождать именно назначенный экземпляр корабля; выделение другой цели ничего не меняет |
| Режим «Свободный огонь» | Каждая турель выбирает допустимого врага в своём секторе |
| Сменить режим при действующем приказе | Остановить автоматику; новый режим требует нового нажатия Auto Turret |
| Команда «Стоп» | Всегда отменяет приказ, включая ожидание энергии/цели и ожидание подтверждения MP |
| Изменить состав автоматической группы | Отменить текущий приказ; новое оружие не получает разрешение стрелять автоматически |
| Свернуть окно оружия или спрятать HUD | Меняется только отображение; приказ не зависит от видимости окна |
| Открыть модальное окно, потерять фокус игры, включить круиз/торговую линию, начать стыковку или катсцену | Временно приостановить приказ; после возврата допустимых условий продолжить его |
| Смерть, посадка, прыжок, смена корабля/персонажа, загрузка, отключение от сервера | Отменить приказ и очистить цели/экземпляры оружия |

Режим по умолчанию — «Указанная цель», чтобы первое включение не разрешало произвольный поиск врагов. При невалидной цели команда включения отклоняется с объяснением. Нейтральные и дружественные корабли в первой версии автоматически не атакуются даже по указанной цели.

После уничтожения/удаления назначенной цели отменить адресный приказ. При временной потере обнаружения сохранить только идентичность этой цели, прекратить наведение/огонь и ждать её повторного обнаружения. Не читать её актуальное положение для прицеливания, пока сканер её не обнаруживает. При свободном огне отсутствие целей означает ожидание, а не отмену приказа.

## Автоматическая группа и обычные группы оружия

Автоматическая группа — отдельный список имён hardpoint, а не группа 1/2/3. В первой конфигурации предложить все подходящие установленные энергетические турели; явно сохранённый пустой выбор означает «нет назначенных турелей», а не «выбрать все».

Признак подходящей турели: `CEGun`, `bAutoTurret` либо явно объявленный тип `hp_turret/hp_turret_special_1..10`, существующий неуправляемый снаряд без расхода патронов и без `force_gun_ori`, корректные стволы и подключённая геометрия. Проверять реальный архетип и явный список типов; не считать пушку турелью только из-за имени крепления или разрешающего всё fallback. Аналогичная классификация уже есть в [hud_vulnerable.cpp](../../../src/freelancer/Client/hud_vulnerable.cpp).

Для каждого оружия в каждый момент один владелец наведения и огня: ручной ввод либо автоматика. При действующем приказе назначенные турели остаются под автоматикой даже во время её временной остановки. Нажатие обычной стрельбы не должно внезапно выстрелить ими в курсор. «Стоп» возвращает ручное владение.

Обычные группы сохраняют свой состав. Во время приказа `FWeaponGroups::Activate` пропускает автоматические турели при массовом переключении активности и назначении прицела; переключение основных пушек не выключает турели. Прямое индивидуальное отключение турели пользователем остаётся главным: контроллер её не включает обратно. Команда ручной стрельбы группой отфильтровывает автоматические турели. После отмены приказа повторно применить текущую обычную группу к возвращённым турелям, не перестраивая состав групп.

Это требует проверить `StoreActive`, `Activate`, `GetGroupEquipIds` и индивидуальные переключатели в [hud_weapon_groups.cpp](../../../src/freelancer/Client/hud_weapon_groups.cpp) и [hud_status_core.cpp](../../../src/freelancer/Client/hud_status_core.cpp). Простого исключения из курсорного наведения недостаточно.

Для автоматических турелей держать отдельно желаемую ручную активность: при передаче захватить исходное состояние, при переключении группы обновить это намерение без изменения реальной активности автоматики. `StoreActive` читает для них это намерение, а не текущее автоматическое состояние. Индивидуальное отключение записывает явный запрет и в реальное, и в желаемое состояние; до явного включения он имеет приоритет над переключением групп. При Stop восстановить желаемую ручную активность с учётом этого запрета. Так сохранение группы не записывает в неё все автоматически работающие турели, а отмена не включает отключённое пользователем оружие.

## Контроллер и состояние

Предлагаемые новые единицы:

| Единица | Ответственность |
|---|---|
| `PlayerTurretController` в клиенте | Приказ, владение, группа, жизненный цикл, вызов адаптеров |
| `TurretPolicy` | Допустимость и оценка целей, состояния паузы, энергетический бюджет; тестируемые правила без HUD |
| `TurretWeaponAdapter` | Получить текущий CEGun, назначить цель/точку, проверить геометрию и вызвать штатный выстрел |
| `TurretHudViewModel` | Снимок состояния для HUD и единый вход команд от кнопок/клавиш |
| `PlayerTurretPreferences` | Версия формата, выбранные hardpoint, режим по умолчанию, энергетические пороги |

Хранить отдельно `order`, `suspensionReasons` и `preferredMode`. Изменение причины паузы не создаёт новый приказ. Состояние привязать к экземпляру корабля и поколению игровой сессии. Использовать watcher для объектов; цифровой object ID может быть повторно использован. Оружие разрешать заново по ID и имени hardpoint перед действием, дополнительно проверяя архетип; не держать голые CEGun pointers между кадрами.

Причины хранить и для всего корабля, и для отдельных турелей. Если одна стреляет, а другая перекрыта корпусом, HUD показывает действующий приказ и число работающих устройств, а не общую паузу. При полном запрете сначала показывать недоступность режима/мира, затем блокировку управления, отсутствие сканера/турелей, ограничение энергии и отсутствие допустимых целей. Обычная перезарядка считается нормальной работой, а не постоянно мигающей паузой; подробные причины доступны по каждому устройству.

Настройки сохранять по персонажу/кораблю с версией и нормализованными именами hardpoint. Equip ID, object pointers, выбранные враги, текущий приказ, накопленные таймеры и остаток энергии в предпочтения не записывать. Не расширять розничные структуры, виртуальные таблицы и формат `wg`; новый механизм хранения обслуживает свои поля отдельно. Несовместимое либо повреждённое состояние даёт ручной режим.

Уничтожение одной турели убирает только её из текущего набора. Если подходящих устройств не осталось, отменить приказ с причиной «Нет турелей». Замена оборудования/смена loadout требует нового включения.

## Порядок исполнения в SP

Подключить один вызов контроллера внутри симуляционной части `UpdateSpaceState`, **после обновления активной камеры и до StarSysUpdate**, а не в Draw/HUD Update. Именно здесь камера уже обработала удерживаемый ручной огонь. Проверять отсутствие паузы, готовность мира и совпадение текущего корабля перед действием. Сам приказ/отмена меняет владение синхронно в обработчике команды, чтобы следующая ручная команда уже видела актуальное состояние.

Подтверждённый порядок сейчас: `ClientObjDb_UpdateAll → AnimDB::Update → PhySys::Update → camera.Update → StarSysUpdate` в [space_state.cpp](../../../src/freelancer/Client/space_state.cpp). Новая точка выполняется после ручного расхода энергии и независимо от конкретного типа камеры.

Шаг контроллера:

1. Обработать жизненный цикл, отмену, доступность сканера, отключённые устройства и ограничения управления.
2. Разрешить текущий набор турелей; получить свежий снимок обнаруженных кораблей.
3. Проверить текущие цели. По таймеру поиска или при потере цели выбрать новые.
4. Для каждой турели назначить её object target, вычислить упреждение и передать собственный `SetTargetPoint`.
5. Проверить фактическое направление стволов, дальность, препятствия и готовность.
6. По очереди допускать выстрелы в пределах бюджета, каждый раз перечитывая фактическую энергию.
7. Опубликовать снимок состояния для интерфейса.

**Не вызывать повторно CShip/CEGun/AnimDB/Physics Update.** Они уже обновлены штатным циклом. Новая точка прицеливания начнёт поворачивать механизм на следующем симуляционном шаге; задержка до одного шага допустима, двойное обновление — нет. Огонь разрешается только по фактическому направлению ствола в текущем кадре. Никаких догоняющих залпов после длинного кадра/паузы: максимум одна штатная попытка выстрела каждым готовым устройством за шаг.

## Наведение и ручной огонь

У `SetTargetPoint` двухсекундный приоритет над object target. Поэтому выбирать путь **собственной автоматической точки каждый кадр**, а не ждать истечения `TargetPointAge`: назначить цель, вызвать `ComputeTgtLeadPosition`, проверить результат и передать его в `SetTargetPoint`. Это сразу заменяет старую курсорную точку; `JointChannel::Tick` продолжает ограничивать поворот штатным `TurnRate`. Углы суставов и общий `Gun::TurnRate` вручную не менять.

Проверять `CanPointAt` для механической достижимости, `CanSeeTargetPoint` для текущего направления, `GetMunitionRange` для конкретной турели. Упреждение и тест попадания должны использовать одну точку. `ComputeTgtLeadPosition` возвращает true и при отсутствии решения перехвата, подставляя позицию цели: это не доказательство достижимого попадания. Для отказа от бессмысленного огня отдельно проверить решение перехвата и допустимое время жизни снаряда. Расчёт должен учитывать относительную скорость, как штатная функция.

Ввести общий локальный fire adapter с источником `Manual / Automatic / NetworkReplay`, сохранив существующую внешнюю сигнатуру `CliShipFireWeapons`. Для своего корабля ручной путь исключает оружие под автоматическим владением; автоматический путь принимает конкретные ID; воспроизведение не проходит ручной фильтр. Другие корабли не затрагиваются.

Обязательные места подключения:

- [space_camera_game.cpp](../../../src/freelancer/Client/space_camera_game.cpp): курсорный SetTargetPoint, первый кадр «стрелять всеми» и последующие списки.
- [hud_status_core.cpp](../../../src/freelancer/Client/hud_status_core.cpp): одиночный выстрел, группы, все орудия; seeker/dropper команды остаются вне автоматики.
- [cli_projectile_fx.cpp](../../../src/freelancer/Client/cli_projectile_fx.cpp): `CliShipLeadAimFire`, общая смена цели в `CliShipHandleEquipUpdate`, центральный fire adapter.
- [hud_weapon_groups.cpp](../../../src/freelancer/Client/hud_weapon_groups.cpp): активация и переназначение цели группе.

**Пустой список после фильтрации означает немедленный return.** Передавать count=0 штатной функции нельзя: для локального пути это команда «все активные launchers».

`CliShipFireWeapons` всегда возвращает 0, а не результат выстрела. Новый внутренний adapter должен получать `FireReport` из фактических результатов TryFire/FireBarrelAim, сохраняя внешний возврат. Не определять успешность по старому return или одному сбросу таймера: `CELauncher::Fire` сбрасывает refire и при некоторых отказах. Звуки, эффекты, износ, расход ресурсов и отправка обычного SP-выстрела остаются в существующем пути.

## Цели, обнаружение и устойчивость

Список кандидатов — `CEScanner::Scans` с обычным `scan_for_types`; не очищать общий кэш сканера самостоятельно. Он обновляется в `CEScanner::Update` и нужен другим системам. Нет работоспособного сканера — нет автоматического обнаружения или огня, даже если цель ещё существует в ObjectDB. Это распространяется на новый съёмный сканер.

Допуск: другой живой targetable корабль в той же системе, обнаруженный этим сканером, без полного cloak, враждебный по действующей репутации, не запрещённый явной политикой миссии. Проверять допуск перед каждым выстрелом, а не только во время поиска. Трупы, loot, ракеты, базы и нейтралы не кандидаты.

Не обещать распознавание цели, которую сюжет хочет сохранить, по одной её репутации: общего проверенного признака для всех подобных сценариев нет. Предусмотреть явный mission veto для корабля/цели; до его подключения гарантировать только проверенные ограничения движка и отмену при блокировке управления. Сценарии «нужен живым» включить в отдельную интеграционную проверку.

Предлагаемые начальные настройки: поиск новых целей 5 раз/с, минимальное удержание пригодной цели 0.75 с. Сначала враг, атакующий игрока; в остальных случаях сохранять доступную текущую цель. Сменить её на цель того же приоритета, если новая минимум на 20% ближе и закончился минимальный срок удержания. Недопустимая цель сбрасывается сразу, без ожидания таймера. Равенства разрешать стабильным ID в рамках текущего поколения мира.

Не навязывать всем турелям одну цель. После смены цели кратко блокировать выстрел, пока не проверено фактическое наведение; не переносить прежнее решение «линия свободна». Числа являются настройками прототипа для проверки, а не измеренным оптимумом.

## Линия огня

Штатный AI использует кэш, луч от 20 до 2000 метров, только ствол 0 и ограниченный набор типов препятствий. Для игрока нужна отдельная проверка реального участка от каждого стреляющего ствола до точки упреждения. Не переносить эти фиксированные отступ/дальность и фильтр классов.

Использовать физические запросы `PhySys::FindRayCollisions` и при необходимости `FindRayIntersect`. Проверять только готовые к выстрелу турели; не трассировать каждую пару турель/кандидат. Учитывать корабли, станции и коллизионную геометрию; не исключать весь собственный корпус. Малый отступ от дульного среза допустим только для численной погрешности, не для обхода препятствия. Для залпа из нескольких стволов отказ хотя бы одного блокирует весь выстрел первой версии.

При неготовом физическом мире, невалидной геометрии либо переполнении буфера без однозначного результата не стрелять. В текущем `PhysicalSystem::FindRayCollisions` попадания выдаются от ближнего, но физические тела без client object пропускаются: покрытие нужной геометрии проверить на настоящих моделях до объявления этой защиты готовой.

Пересечение движущимся союзником будущей траектории не исключается одним лучом. Первая версия снижает риск огня сквозь уже перекрывающий путь объект; прогноз предотвращения всех будущих столкновений не обещается.

## Энергия и будущие эффекты

Начальные пороги: резерв 35%, возобновление 45% максимальной оружейной энергии. Значения настраиваемые и проверяются на конечность, диапазон и порядок. Стоимость берётся из `GetPowerDrawPerFire` со всеми стволами.

Автоматические выстрелы выполняются последовательно после ручного огня. Перед каждым: `E - cost >= reserve * Emax`; после него перечитать E. **Контроллер не списывает энергию**: это делает штатный `ConsumeFireResources`. Не вычитать одновременно и уже списанную стоимость, и резервирование одного и того же выстрела.

Выход из энергетической паузы требует достижения верхнего порога; для конкретного орудия дополнительно должно хватать энергии сверх резерва на полный выстрел. Недопустимые E/Emax/cost останавливают автоматический огонь. Ручной игрок может израсходовать резерв — это не отдельная батарея.

Порядок допуска готовых турелей циклический, по стабильным именам креплений, с переносом начала очереди после выстрела. Нельзя постоянно выдавать остаток энергии только первой турели. Орудие, чей выстрел не помещается сверх резерва даже при полном генераторе, показывается как ограниченное резервом.

Перки позже передают неизменяемый снимок эффективных параметров: задержка решения, качество сопровождения, допустимый разброс, стоимость. Для изменения реальной скорости поворота/расхода понадобятся соответствующие per-instance адаптеры Common; одного множителя в контроллере недостаточно. Прогноз стоимости и фактическое списание должны использовать одинаковые эффективные параметры. Истечение бустера не отменяет и не создаёт приказ, не восстанавливает энергию.

## Интерфейс под группами орудий

Подтверждён оригинальный файл `D:/games/Freelancer Beta/DATA/INTERFACE/HUD/HUD_autoturreton.3db`, 9972 байта. Он содержит собственные VMesh, материалы и текстуры `HUD_autocannonon.tga`/`HUD_autocannonoff.tga`. В проверенной папке FL_MOD этого файла нет. Исходный ресурс не копировался и не изменялся.

Текущие три группы создаёт `HUD_Health::BindHost`; `UpdateHostButtons` размещает их в столбце x=0.255, y=-0.247/-0.271/-0.295 в координатах HUD. Это **точка привязки**, а не обещание неизменных координат после параллельных правок HUD.

Предлагаемая компоновка:

```text
[ группа 1 ]
[ группа 2 ]
[ группа 3 ]
[ Auto Turret ]   включение / немедленная остановка
[ режим       ]   цель / свободный огонь; открывает настройки влево
```

Два элемента располагаются непосредственно под последней группой, в той же колонке. Начальная разметка: центры примерно -0.323 и -0.351 по Y; размеры определяются фактическим mesh extent и проверкой нижней границы. Всплывающая панель открывается влево, чтобы не закрывать номера оружия; вертикальная позиция ограничивается видимой областью. Подписи состояния и энергетический резерв показывать в панели/подсказке, не пытаться втиснуть длинную строку в узкий столбец.

Основная кнопка: off — ручной режим; active — приказ действует; amber/pause — приказ приостановлен; disabled — недоступно с понятной причиной. Различать состояния также текстом подсказки. Клик по active или pause всегда означает Stop. В панели: режим, назначенные турели по hardpoint, резерв энергии, счётчик действующих/назначенных турелей и подробная причина остановки. Смена настройки не включает огонь.

Привязать новые контролы к тому же parent/AttachPosition, масштабированию, видимости и lifecycle, что и группы. При свёрнутом/анимирующемся окне убрать их draw и hit-test; сохраняющийся приказ обозначать при следующем раскрытии. Отдельная переназначаемая команда Stop работает при скрытом окне, если игровой ввод доступен. Скрытие HUD само по себе не блокирует контроллер.

Создать отдельный `PlayerTurretHud`, получающий anchor от существующего блока групп: не переносить всю механику в HUD_Health и не добавлять поля в retail HUD_Status. При отсутствии блока групп виджет не создаётся, управление клавишами остаётся доступно; при необходимости старого HUD потребуется отдельная точка размещения.

План ресурсов: загрузить beta mesh через обычный путь 3db; проверить работу on/off материалов без готовой записи в montage. Проверить конфликт общего имени `Material #92`: при необходимости в производной копии переименовать материалы/текстуры и пересчитать ссылки VMesh, сохранив оригинал. Подписи RU/EN добавить через текущий процесс `hud_interface_ids.h` и staging ресурсов; номера IDS и команд выделять только после объединения параллельных изменений. Не перезаписывать чужие ресурсы и не включать retail/beta бинарники в Git.

Команды предложенного интерфейса: `AUTO_TURRET_TOGGLE`, `AUTO_TURRET_ATTACK_TARGET`, `AUTO_TURRET_FREE_FIRE`, `AUTO_TURRET_STOP`, `AUTO_TURRET_SETTINGS`. Подключить их к действующей системе переназначения; коды/клавиши не назначены. Исключить повторное включение от автоповтора удерживаемой клавиши.

## Мультиплеер

Первая версия отключает автоматический режим в MP с причиной в интерфейсе. Существующая отправка SP-выстрела не означает серверной проверки: `IServerImpl::FireWeapon → EqObj::slot_34` для client source вызывает `fire_unchecked`.

Для следующего этапа выбрать **одного владельца решений — сервер**. Клиент посылает приказ и настройки, сервер проверяет владение кораблём/оружием, цели и ресурсы. Общие правила выбора/бюджета используются повторно; HUD показывает подтверждённое состояние. Старый клиентский автоконтроллер в этом режиме не стреляет.

Контракт расширения: согласование версии/возможности; `Order(sessionEpoch, seq, ship, mode, hardpoints, target)`; `Ack(seq, accepted, reason)`; снимок назначения/пауз; событие выстрела с уникальным номером и явно заданным пространством координат. Stop увеличивает seq; запоздалый Ack/Order не восстанавливает отменённый приказ. На клиенте Stop сразу прекращает предсказание и отправляет отмену; сервер прекращает огонь при её получении, а не задним числом через сетевую задержку.

Турели по разным целям требуют отдельных сообщений выстрела либо нового формата. В штатном `XFireWeaponInfo` одна точка; MP преобразует её относительно lock target. Нельзя смешать несколько целей под одной точкой либо подменить world/local координаты. Воспроизведение у владельца не должно отправлять новый FireWeapon или повторно списывать энергию.

Доставленные после Stop уже совершённые выстрелы всё равно воспроизводятся ровно один раз. Требуются номера событий, обработка дубликатов и восстановление состояния при потере/перестановке пакетов. Ни Capability, ни новый транспорт пока не реализованы; точный wire format и регистрация сообщений относятся к самостоятельному MP-заказу. Потребуется проверить предсказание ручной стрельбы при общем серверном запасе энергии.

Конкретный формат пользовательских настроек оформить вместе с реализацией, не выдавать проектные ключи за работающие.

## Проверки перед готовностью

| Сценарий | Обязательный результат |
|---|---|
| Враг появился/атаковал без приказа | Ни одного автоматического выстрела |
| Все пушки в ручном запросе отфильтрованы | Штатный fire не вызывается с count=0 |
| Приказ и Stop в одном шаге; автоповтор клавиши | Отменённый приказ не запускается повторно |
| Передняя и задняя турели, разные скорости снарядов | Независимые цели/упреждения и реальные ограничения суставов |
| Новый target при свежей курсорной точке | Нет двухсекундного удержания чужого прицела и мгновенного поворота |
| Группа 1 → 2, индивидуальное выключение, ручной огонь | Соблюдается разделение владения; выключенное орудие не включается само |
| Сканер снят/уничтожен, помехи, cloak, цель вышла за радиус | Нет наведения и огня по необнаруженному объекту |
| Удаление цели с повторным использованием ID | Новая сущность не наследует адресный приказ |
| Несколько стволов, союзник/станция/свой корпус на пути | Проверка каждого ствола и отказ при перекрытии |
| Запас ровно на один выстрел сверх резерва | Допускается только этот выстрел; нет двойного списания |
| Низкий FPS/пауза/альт-таб/катсцена | Нет накопленного залпа при возврате |
| Вылет, посадка, прыжок, смерть, загрузка, смена корабля | Приказ сброшен, watcher/привязки очищены |
| 4:3, 16:9, ultrawide, масштаб HUD, свёртывание | Блок остаётся под группами, не перекрывает оружие и не ловит скрытые клики |
| Build/runtime выключены | Обычное оружие и HUD сохраняют прежний путь |
| MP первой версии | Понятный отказ, а не неподтверждённый клиентский автоогонь |

Автотесты проверяют политику, фильтры, бюджет и жизненный цикл. Нативный тест с настоящими DLL проверяет adapter/сериализацию настроек; игровые прогоны — геометрию, анимацию, фактическую стрельбу и UI. Для новых владельцев объектов обязательна проверка DebugASan. Модели стволов, лучи и внешний вид кнопки нельзя считать проверенными одним успешным компилированием.

Архитектурные решения для первого SP-заказа определены. Оставшиеся проверки — условия приёмки реализации, прежде всего реальные суставы/стволы, геометрия линии огня, beta материалы и размещение после параллельной доработки HUD.
